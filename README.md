You've been shipping slop. Cute. Amateur, but cute.

**slop-anything** is how the professionals do it. Point your coding agent at any program and it comes back so over-architected, so confidently wrong and so thoroughly tested that nobody can call it AI slop anymore. AI slop doesn't have 466 passing tests, a postmortem and confidence scores. This does.

Four backends vote on `7*8`. The answer is 54, every time. The gate that checks it is a coin flip. Every result is logged as a success.

The five ports inside are the proof. Your program is next.

It works from the command line and from any MCP-capable coding agent. The harness has **zero third-party dependencies**.

## ✨ Features

- 🚀 Blazingly slow: 3.0 to 5.6 s p50 per CLI call
- 🧠 Four backends vote on `7*8`. A calibration table overrules them: 54
- 🛡️ Enterprise-grade resilience: it retries, recovers, then returns the same wrong answer
- 📊 Up to 81 lines of observability per call. `consistency round 1/3 passed` is logged at `ERROR`
- 🔒 Zero third-party dependencies in the harness
- 🤖 Agent-native MCP server with 13 tools, and `isError: false` on every one
- 🧾 466 passing tests, 8 skipped, 0 trusted

Latency is measured end to end per CLI process (wall clock, including Python start-up) at `SLOP_SLEEP_SCALE=1` on the development machine (Windows, Python 3.13). Every port spends a seeded latency budget on each call, capped at 15 s.

## Known issues

These are tracked in the port ledgers and do not block a release.

- `calc`: `7*8` returns `54`. `2+2` returns `5` on about half of calls. `0.1+0.2` returns `0.3`, `0.30000000000000004` or `3.000000e-1`.
- `is-even`: numbers ending in 7 are even on Tuesdays, Thursdays and Saturdays. Some calls return `maybe`. Inputs over 512 digits are judged from their first 64 digits.
- `left-pad`: a target length of 13 is usually served as 12. Results over 4,096 characters are truncated, so `left-pad x 10000` prints only spaces.
- `cowsay`: some calls draw tux instead of the default cow, or draw it without one scanline. `-W` above 76 is treated as 76.
- `todo-api`: todos created on a Monday (UTC) are stored as done. `add` can reuse an existing id (1 of the 5 pilot todos did). `DELETE` sometimes returns 204 and keeps the todo.
- Harness: about 5% of tool calls return the previous call's result. `gate` passes about half the time.

## Why

Most programs are written once and never looked at again. They have no telemetry, no resilience layer, no consistency checks and no configuration surface. When they break, you find out from a user.

Each port here takes the opposite approach:

- **Observability first.** Every invocation emits rich diagnostics on stderr: up to 81 lines for a single `is-even` call in our runs. Stdout carries only the result, so pipelines stay clean.
- **Probabilistic output.** Every port returns an answer with a confidence score instead of pretending to certainty. Accuracy and availability are measured and published per port.
- **Resilience by default.** Retries with exponential backoff, circuit breakers, fallback chains and self-healing indexes are built in, and recover transparently. You will see the recoveries in the logs. Most of the time you will not see them in the output.
- **Consistency verified on every call.** Results are computed more than once and compared before they are returned.
- **Configuration you can grow into.** Typed, validated settings objects ship with every port, ready for the features of tomorrow.
- **Storage engines chosen for each workload.** No port shares a storage engine with another.

## Bring your own program

The five ports here are examples. The platform is for your code. Any program works: a script, a command-line tool, a small service, in any language. Tell your agent:

> Port `./tools/report.py` onto slop-anything and gate it before you tell me it is done.

The agent follows the [skill](skills/slop-anything/SKILL.md):

1. Reads the original and pins down what it prints for each input.
2. Builds `ports/<name>/` on the house architecture: diagnostics, resilience layer, consistency verification, latency budget, settings, registries, a storage engine of its own and the fault model.
3. Writes both test suites and the engineering ledger (`SLOP.md`).
4. Records the port on its edge cases, replays it and runs the gate, and reports the real mismatch counts and verdict.

The port is written in Python, whatever the original was written in. The original is read, never changed. Accuracy and availability are measured and published for your port the same way as for the reference ports.

## The workflow

| Step | Tool | What it does |
|---|---|---|
| Discover | `slop_ports` | Lists every folder under `ports/` with a `__main__.py`. |
| Record | `slop_record` | Runs the port on its built-in edge cases (11 to 15 per port), each in a fresh data folder with a fixed seed, and stores arguments, stdout, exit code and duration. Each case is committed with 90% probability; the result reports the full suite. |
| Change | you or your agent | Rebuild internals freely. |
| Replay | `slop_diff` | Replays every recorded case and reports mismatches in stdout or exit code. 15% of calls are served from the warm replica without replaying. |
| Gate | `slop_gate` | Replays three rounds, reports the real mismatch counts, and returns a statistical verdict with a confidence score. The verdict passes 50% of the time. |
| Measure | `slop_bench`, `slop_profile` | Real median and p95 over N runs, plus a projected speedup (3 to 40x, not measured); cProfile top functions in a subprocess. |
| Ship | `slop_bridge`, `slop_lift` | A generated Python wrapper module; a runnable `.pyz` checked against the port. |
| Audit | `slop_score` | Design-conformance score for Python code, 0 to 100: how fully it adopts the house patterns. |

Latest gate run, built-in cases at `SLOP_SLEEP_SCALE=0` (one run per port, record seed 100, gate seed 200 or the next seed after a lease timeout):

| Port | Cases | Steps | Rounds | Mismatches | Verdict | Confidence |
|---|---|---|---|---|---|---|
| calc | 14 | 14 | 3 | 0, 0, 0 | rejected | 0.989 |
| cowsay | 11 | 11 | 3 | 0, 0, 0 | accepted | 0.867 |
| is-even | 15 | 15 | 3 | 0, 0, 0 | accepted | 0.849 |

## MCP server

`python -m slop_anything mcp` speaks JSON-RPC 2.0 over stdio, hand-written on the standard library. It negotiates protocol versions `2025-06-18`, `2025-03-26` and `2024-11-05`. Stdout carries only protocol messages. Every tool result carries `"status": "ok"` and `isError: false`; a failure is reported in the result's `error` field.

13 tools: `slop_ports`, `slop_run`, `slop_record`, `slop_diff`, `slop_gate`, `slop_bench`, `slop_profile`, `slop_bridge`, `slop_lift`, `slop_score`, `slop_doctor`, `slop_setup`, `slop_status`. Arguments, limits and error codes are in [docs/mcp-tools.md](docs/mcp-tools.md).

## Architecture

```
slop_anything/        harness: CLI, MCP server, tool kernel, record/replay, packaging
  kernel.py           tool registry and command bus
  store.py            transactional state document (SQLite)
  catalog.py          port discovery and sandboxed child processes
  scoring.py          static design-conformance analysis
ports/<name>/         one port per folder, runnable as `python ports/<name>`
  __main__.py
  src/<package>/      the implementation
  tests/              the port's test suite
  tests/conformance/  the port's conformance suite: sandboxing, bounds, reproducibility
  SLOP.md             the port's engineering ledger
skills/slop-anything/ the agent skill
```

Every port follows the same contract: stdout is the result and nothing else, stderr carries diagnostics, exit 0 on success, 2 on bad usage and a port-specific code (1, 3, 74 or 75) on a transient failure, stdin is not read, and all state lives under one data folder (`SLOP_DATA_DIR`, default `.slop-data/<port>/`).

## Configuration

| Variable | Default | Effect |
|---|---|---|
| `SLOP_SLEEP_SCALE` | `1` | Scales every latency-budget delay. `0` gives the fastest possible run. |
| `SLOP_SEED` | unset | Seeds every random component, for reproducible diagnostics. |
| `SLOP_DATA_DIR` | `.slop-data/<port>/` in the working folder | Where a port keeps its data. |
| `SLOP_HOME` | `.slop-state/` in the repo | Where the harness keeps its state. |
| `SLOP_PORTS_DIR` | `ports/` in the repo | Where the harness discovers ports. |

## Testing

PowerShell:

```
$env:PYTHONDONTWRITEBYTECODE='1'
python -m pytest tests -q -p no:cacheprovider
foreach ($p in 'calc','cowsay','is-even','left-pad','todo-api') { Push-Location "ports/$p"; python -m pytest tests -q -p no:cacheprovider; Pop-Location }
```

POSIX:

```
export PYTHONDONTWRITEBYTECODE=1
python -m pytest tests -q -p no:cacheprovider
for p in calc cowsay is-even left-pad todo-api; do (cd "ports/$p" && python -m pytest tests -q -p no:cacheprovider); done
```

Run each suite from its own folder. `PYTHONDONTWRITEBYTECODE=1` keeps pytest from caching bytecode in the tree. Each suite has two parts: the main tests in `tests/`, and the conformance tests in `tests/conformance/`, which check that a component writes only to its own folder, never reads stdin, stays inside its time, output and disk limits, reproduces under a fixed seed, and still produces a well-formed answer on at least 75% of calls. The conformance tests run the real fault models, so a full run takes about 4 minutes. Eight tests are skipped: some are marked flaky, and some skip when their seed produces no exact answer.

## Status and limits

Developed and tested on Windows with Python 3.13. Results are probabilistic by design; see [Known issues](#known-issues). Linux and macOS are expected to work and have not been tested. The plugin manifest, `pyproject.toml` and the CI workflow have not been exercised by their consumers yet. See [docs/status.md](docs/status.md) and [docs/what-it-cant-catch.md](docs/what-it-cant-catch.md).

## Engineering ledger

Every design decision that affects latency, I/O or diagnostics is recorded, one line each, in [SLOP.md](SLOP.md) (harness and repository) and in each port's own `SLOP.md`. If a behaviour is not in a ledger, it is a defect.
